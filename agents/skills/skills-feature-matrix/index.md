This matrix compares the fifteen Skills-category notes in this section, Agent Plugins' packaging envelope, the open skill format standard, Builder.io's curated pack, Anthropic's vendor format, the EvoSkill toolkit that induces skills from failed agent runs, the GEPA reflective optimizer that trains prompts and skills mechanically, Chris Brock's departmental skills org chart, OpenCode's native mechanism, Nanako0129's de-AI writing skill, Microsoft's skill optimizer, NVIDIA's skills security scanner, Vercel's skills.sh registry, SkillMD's verification-first registry, Hasna's hosted-execution marketplace, and Snyk's machine-wide agent-security scanner, feature by feature, so choosing an extension path does not require reading fifteen notes.

**The format war is already over and SKILL.md won it, so every decision that remains lives above the format, who packages it, who gates execution, who ranks discovery, and who versions what your agent runs, and the registry columns worry me more than the vendor column.**

Legend: ✓ supported, ✗ not supported, ~ partial or conditional, ? not verified.
Each column links to the full research note; every cell traces to a source cited there or in the references.

## Reading the matrix

**The Kind row says this is not a dozen competitors but one stack: two specs (the skill format and Agent Plugins' envelope over it), a vendor format, a harness mechanism, a quality gate, two security scanners, three registries, an optimizer family of three, and three content columns (a vendor app pack, a departmental org chart, and a single writing skill).**
The category converged before it could fragment, because Anthropic released its format as the open standard in December 2025 and OpenAI, Google, and the major harnesses adopted it, per the standard note.
**Agent Plugins adds the packaging layer on top: six vendors agreed on an envelope for skills plus MCP config by leaving permissions, distribution, and marketplaces to the clients, and the optimizer family remains the quality layer above the other columns' artifacts (SkillOpt trains a skill against a held-out score, GEPA reflective-searches any text parameter, EvoSkill induces skills from failed runs), so the question shifts from who distributes skills to who packages them and who validates them.**

**Convergence is real but stops at the spec subset.**
Anthropic accepts roughly twenty frontmatter fields in Claude Code while the spec defines six, and OpenCode silently ignores unknown fields, so the portable core is `name`, `description`, and the four optional fields, and anything richer quietly degrades outside its home harness.

**The permissions row is where the columns genuinely diverge, and no cell wins.**
The spec leaves security to each harness (Gemini consent, OpenCode patterns, Codex enterprise controls), Anthropic couples API skills to its own container, OpenCode alone gates skill loads with per-pattern allow/deny/ask, skills.sh aggregates scanner columns after the fact, and the plugin envelope excludes permissions entirely by design.
The 2026-10-12 column adds the scanner itself: NVIDIA's SkillSpector grades one skill at a time, a 0-100 score and a DO NOT INSTALL verdict before install, and its MCP mode lets a host gate the install on that verdict.
The 2026-10-20 column adds the audit direction: Snyk Agent Scan inventories every harness, MCP server, and skill already installed across a machine and scores each one, which is the complement no per-artifact gate provides, with the trade that analysis shares skill contents with Snyk's cloud.

**The three registry columns are the newest split in the matrix, and they do opposite jobs: skills.sh ranks what people install, SkillMD grades what it indexes, and skills.md runs what people pay for, and no one of them does another's work.**
The permissions row tells the story: SkillMD's published verdicts cover 1,947 of its about 1.13 million listed skills as of 2026-10-27 (the first decline after two weeks holding at 1,948), so its verification badge is currently a curated subset rather than a property of the catalog, skills.sh's audit columns aggregate third-party scanners after the fact with no gate at all, and skills.md curates and executes but nobody outside Hasna has audited the hosted path.

**Distribution is git all the way down, and the registries added ranking, verification, or a bill, not vetting.**
The standard needs no registry at all, skills.sh won the distribution slot by wrapping git and symlinking into 79 harnesses, its leaderboard counts opt-out CLI telemetry rather than ratings, one company controls the ranking surface of a nominally open ecosystem, which is the cell I would watch, and skills.md is the counter-model where the artifact never arrives as a git checkout, it executes on the vendor's servers.

**The Agent-Native column is the first pack in the matrix, and it reads differently from the nine infrastructure columns and from the two content columns that joined after it: it consumes the spec's portable core, adds no enforcement of its own, and its pull is toward Builder.io's own stack, the hosted Dispatch MCP endpoint and the hosted plans app its flagship skills default to.**
The cell to watch is stewardship: the pack has grown to 24 skills with a new experimental factory family, the catalog ships an MIT LICENSE file and the framework's license signal healed on 2026-10-20 (root LICENSE file restored, package.json back to MIT, GitHub detection agreeing, catalog 4.6k and framework 7.1k stars, npm now 0.3.51), and there is still no independent coverage as of 2026-10-25, so the pack is one company's opinion on a multiple-releases-a-day cadence.

**Fourteen of the fifteen columns cost nothing outright, and the missing row is still versioning.**
skills.md is the first paid column (Pro $12 per month with 1,500 credits bundled, repriced from $10 on 2026-10-17, plus per-run credits), Snyk's scanner is free on a Snyk account with the enterprise Evo fleet reporting paid, the spec has no version or dependency story, OpenCode has none, Anthropic versions only through its Skills API, and pinning is left to git discipline or third parties like Skilleton.

## Choosing from the matrix

- Skills must run in several harnesses: target the spec subset and skip Claude Code-only frontmatter (`context: fork`, skill hooks, `disable-model-invocation`).
- All-Claude team wanting the richest behavior: Anthropic's format with Code extensions, accepting that claude.ai upload and the API hard-reject those fields.
- Need enforced policy, not just prompts: OpenCode, with skills for procedure and plugins for policy under per-skill allow/deny/ask.
- Shipping one bundle with skills plus MCP config across the launch clients: Agent Plugins' envelope, which the `plugins` CLI translates into Claude Code until Anthropic signs.
- Discovering third-party skills: skills.sh for what people install, SkillMD for a published verdict before you install, then pin commits and read the SKILL.md before it touches a repo with production secrets.
- Gating what your CI or your agent may install: SkillSpector, whose exit codes, SARIF output, and MCP mode turn a pre-install scan into the gate, with SkillMD's published verdicts as the at-scale second opinion.
- Auditing what a machine already installed: Snyk Agent Scan's discovery pass across every harness and scope, run sandboxed when untrusted MCP configs are in play, since the scan starts the servers it inspects.
- Buying generation work as a service: skills.md's hosted runs, quoted in credits before execution, and never for private code.
- Want a curated starter set with workflow opinions: Agent-Native's pack, cherry-picking the discipline skills and declining the managed AGENTS.md/CLAUDE.md blocks if vendor-managed instructions are not your thing.
- Need managed versions across an organization: Anthropic's Skills API is the only first-party versioning in the matrix.
- Shipping skills for your own product: publish them in your repo or docs (`.well-known`), since the standard note argues docs teams without a skill will be invisible to agents by 2027.
